  - Enterは改行だけを入れ、URLを貼ってもリンクの記法にしない。TABは今までと同じく文字のタブを入れる（フォーカスした直後とESCの後は次の欄へ）

  - `codemirror.min.js`が読めないときは、今までのtextareaのまま

### システム

- FastCGIで動かしているとき、`lyndbaum.fcgi`を書き換えた後にリクエストが来ると、スレッドが3秒ごとに10本ずつ際限なく増え、メモリを使い切っていた問題を修正（終わったスレッドの数ではなく、常に起動時の本数を作り足していた）
  - 事象（推定）
    - `lyndbaum.fcgi`の動作中にこのファイルが書き換わった後に一回でもリクエストを受けると3秒ごとに10スレッド増え続けOOMを引き起こしていた
      - lyndbaum.fcgi:64-71が該当箇所で[元のadiaryの2020年のコミットab4aee99](https://github.com/nabe-abk/adiary/commit/ab4aee99#diff-9395899baf8349484fcf50f4cdb9fd9df8b9f295dc7fdfaf573985aa40bf2188R54-R60)から存在していた模様。
      - スレッドの増分は引数で指定していた数分増えていた
        - 本来は何本スレッドを生やすかを決めるもの
      - リクエストが来たときにスレッドが消費され、`$exit_threads`が`-1`になり、`if (!$exit_threads) { next; }`が偽となった結果、`&create_threads( $Threads, $Socket );`され、無限増殖していた
        - 今回は`$exit_threads < 1`としたことで、減った分のスレッドだけを補充し、スレッド数に変化がないか負の値の時はスレッドを生成しないようにした
    - 以後、リクエストが来なくても3秒ごとに10本ずつスレッドが増え続け、無限増殖でOOMを引き起こしていた
    - [本家にPR提出済](https://github.com/nabe-abk/adiary/pull/19)
  - 原因
    - スレッドが終わる条件は`if ($modtime != (stat($0))[9]) { last; }`で、`lyndbaum.fcgi`の更新時刻が起動時と違うときにリクエストを1件処理すると成り立っていた （ファイルが消えているときも同じ）
    - 公開ディレクトリが作業ディレクトリへのシンボリックリンクであるときに、このファイルが書き換わったり、名前の変更の行き来で消えたりするが、それ以降に開発サイトを開くと、暴走が始まっていた
    - 増え方は約0.28GB/分であった
- ログイン中の画面は、`Cache-Control: private, no-store`にして、途中のキャッシュにもブラウザーにも保存させないようにした（ログインしていない人の画面は今までどおり`no-cache`）
- adiary向けのpingが失敗する問題を修正

### 開発・ドキュメント

- デバッグ方法（`docs/デバッグ方法.md`）を分かりやすく書き直し、`.vscode/launch.json`から`lyndbaum.cgi`を直接動かす構成を消した
