# 性能の測り方

Lyndbaumはadiaryの機能を減らしたものなので、同じ画面ならadiaryより速くなければおかしい。遅くなったら、機能を削って埋め合わせず、原因を直す。

## 比べるときの決まり

ベンチマークの数字は条件で簡単に変わる。比べるときは次を揃える。

1. **両方を起動し直す**：常駐プロセスは、ライブラリの再読み込みや多様なURLの処理で遅くなる。起動してからの時間が違うものは比べられない
2. **ウォームアップする**：最初のリクエストはスケルトンの読み込みなどで遅いので、捨てる
3. **起動し直して、交互に測る**：同じプロセスの中では値が揃っていても、起動し直すと値がずれる（動作の同じコードでも差が出る）。1回の起動の数字では比べず、起動し直して5回以上測る。起動ごとの中央値を集め、その中央値と範囲を見る。範囲が重なる差は、差と言わない
4. **クライアントを頭打ちにしない**：`ab -c 100`はTLSの処理で`ab`自身のCPUが100%になり、サーバーの差を測れない。実行中に`top`で確かめる。並列で測るときは、ソケットへ直接つなぐか、クライアントを複数のプロセスに分ける
5. **CPU時間も見る**：`/proc/プロセスID/task/*/schedstat`の1列目（ナノ秒）の増えた分を、リクエスト数で割る。ネットワークの揺れの影響を受けない
6. **低い頻度でも測る**：1秒に数件の間隔で測る。時間でキャッシュする作りは、連続で叩くときだけ速く見える

## どこが遅いかを調べる

- 関数ごとの時間は`Devel::NYTProf`で見る。プロファイラの下では実際より数倍遅くなるので、割合と回数を見て、時間そのものは比べない
- ファイルへの問い合わせは`strace -c`で数え、中身は`strace -e trace=newfstatat`で見る
- 直したら、1つずつ積み上げて測る。効果が振れ幅に収まるものは入れない

## 性能の予算

`t/performance_budget.t`が、トップページ1回の次の回数に上限を設けている。時間ではなく回数を見るので揺れない。pushの前のチェックで動くので、超えるとpushできない。

| 項目                         | 変数           |
| ---------------------------- | -------------- |
| スケルトンの呼び出し         | `$CALL_MAX`    |
| システムコール               | `$SYSCALL_MAX` |

## 開発するときの決まり

次のことをしたら、予算の値を確かめる。

- `skel/_sub/`のスケルトンを足す。記事ごとに呼ぶものは、記事の数だけ呼び出しが増える
- 記事ごと、モジュールごとに走る処理を足す
- ファイルの更新日時を見る処理を足す（画面に読み込むファイルを足すときも増える）

上限を上げるのは、機能のために必要なときだけにする。上げるときは、理由を変更履歴に書く。
